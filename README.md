# ADAIG Portal

Association for Data and AI Governance member & public portal. Next.js 16 (App Router) · React 19 · TypeScript · Tailwind v4 (utilities only) + the ADAIG design system in `src/styles/` (`tokens.css` → `base.css` → `components.css` → `shell.css`, then one file per area: `chrome.css`, `home.css`, `pages.css`, `member.css`, `admin.css`; imported in that order by `src/app/globals.css`) · Prisma 7 on Supabase Postgres · Auth.js v5 · next-intl (EN/FR) · Stripe (test mode, with mock fallback; used for paid event tickets only).

## Run locally (online Supabase)
Requirements: Node 26 (`.nvmrc`; any Node `^22.12 || >=24` works) and a Supabase project (use a **development** project, not production).
```bash
cp .env.example .env            # paste DATABASE_URL / DIRECT_URL from Supabase → Connect → ORMs → Prisma; set AUTH_SECRET (openssl rand -base64 32)
npm install                     # also runs `prisma generate` (client in src/generated/prisma, gitignored)
npx prisma migrate deploy       # create/upgrade the tables (+ RLS lockdown); `npm run db:check-rls` verifies it
ALLOW_REMOTE_DB=1 SEED_PASSWORD="<12+ chars>" npm run db:seed   # once, on an empty DEVELOPMENT database: demo accounts + events
npm run dev                     # http://localhost:3000  (→ /en)
npm run build && npm start      # production build
```
Seed logins: `admin@adaig.test` (Super Admin), `admin2@adaig.test` (Super Admin), `member@adaig.test` (active Professional), `guest@adaig.test` (free guest), all with the `SEED_PASSWORD` you chose (on a `localhost` database the seed defaults to `Password123!`). The seed wipes the tables, so it refuses any non-local database (host other than `localhost`/`127.0.0.1`/`::1`) unless `ALLOW_REMOTE_DB=1` is set for that command, and a database that already has users unless `SEED_FORCE=1`. Offline alternative: `npx supabase start` (Docker) and the local URLs noted in `.env.example`.

**Never point a local `.env` at production.** Every tool that can delete data checks the database host first (`scripts/lib/db-guard.ts`): `npm run db:reset`, `npm run db:migrate`, `prisma migrate reset|dev` and `prisma db push` (in `prisma.config.ts`), the seed, and the e2e suite refuse a non-local host unless `ALLOW_REMOTE_DB=1` is set for that one command. The maintenance scripts (`unlock`, `expire-unpaid-orders`, the one-off fixes) print which host they use (`[db] REMOTE database host: …`) before doing anything.

Useful commands: `npm run lint` (ESLint CLI; `next lint` no longer exists), `npm run typecheck`, `npm run db:seed` (re-seed: wipes the app tables), `npm run db:reset` (drop + re-apply all migrations + seed; local databases only), `npm run db:migrate` (`prisma migrate dev`, local only), `npm run db:check-rls`, `npx prisma studio`. Health check: `GET /api/health` → `{ "ok": true, "db": "up" }` (503 with `"down"` when the database does not answer).

## Architecture
- **Next.js 16 App Router**: pages are React Server Components that read the database directly (`src/lib/db.ts`); mutations are Server Actions (`actions.ts` next to each page). Route handlers only for the CSV/JSON exports (`/api/admin/*.csv`, `/api/me/export`), the Stripe webhook, Auth.js, the daily cron job (`/api/cron/*`) and `/api/health`. Turbopack builds dev and production.
- **Prisma 7** with the `prisma-client` generator (`src/generated/prisma`) and the **`@prisma/adapter-pg`** driver adapter (node-postgres; no Rust query engine). The runtime uses the pooled URL with a small pool (`DB_POOL_MAX`, default 5); the CLI (`prisma.config.ts`), seed and scripts use the direct URL. Server environment is validated with zod in `src/lib/env.ts` (secrets never reach the browser).
- **Supabase Postgres** is the only database. Schema history is versioned in `prisma/migrations` (`prisma migrate dev` locally, `prisma migrate deploy` on Vercel). Row Level Security is enabled on every `public` table with no policies, and the Data API roles `anon`/`authenticated` have no grants, so Supabase's REST/GraphQL API exposes nothing; the app connects as the table owner and is unaffected. `scripts/check-rls.mjs` fails if a table is missing RLS.
- **Auth.js v5** (credentials provider, JWT sessions valid for 7 days, renewed while in use). The JWT holds only the user id and `sessionVersion`; role, active flag and Admin Portal permissions are re-read from the database on every session lookup (never trusted from the token). Signing out ends the session on that device; a staff password reset, a member's own password change (Profile → Change password), account deletion, and in Admin → Users a role change, deactivation or password reset end every session (`User.sessionVersion`). Deactivated accounts (`User.active = false`) cannot sign in, their sessions stop on the next request, and their outstanding password reset links are deleted (they stay dead after a reactivation). Login throttling and the anonymous-write rate limits live in the `LoginThrottle` table.
- **Admin Portal access control (RBAC)**: admin accounts (`role = "admin"`) hold one `AdminRole` whose permissions are modules × actions; every admin page, server action and admin API route checks them on the server (`src/lib/rbac.ts`). See "Admin Portal users & roles".
- **next-intl** (EN/FR, `/en` and `/fr` prefixes) and a **per-request nonce CSP**, both in `src/proxy.ts` (Next.js 16's name for middleware; Node.js runtime).

## Configuration — founder decisions in ONE file
`src/config/site.ts` holds **locales, currencies (USD only; CAD kept for display of historic payments and can be re-enabled by adding it to `currencies`), membership tiers (names EN/FR, descriptions, prices per currency, benefits), US state sales-tax table (empty = no tax), US states/DC/territories and Canadian provinces (address only)**. Membership page, join, dashboard and admin all read tiers through `src/lib/settings.ts`; the DB stores only the tier id. The values in `site.ts` are the **defaults**: staff can override tier names/descriptions/benefits (EN/FR), order, visibility, “most popular” and eligibility checks, the public contact details and the operational policies in **Admin → Settings** (`Setting` table, effective on the next request; “Reset to default” removes the override). Tier ids and prices stay in code. Tier prices in the config are not shown publicly (dues are still being finalized; the point of contact confirms them after an application). The "Compare benefits" table, enterprise section and FAQ on /membership come from `src/content/<locale>/membership.html`.

## Database
Supabase Postgres, locally via the Supabase CLI and in production via Supabase on Vercel (see "Deploying to Vercel"). To change the schema: edit `prisma/schema.prisma`, run `npx prisma migrate dev --name <change>` (creates and applies a new folder in `prisma/migrations`; then `npx prisma generate`), commit the folder. New tables need `ALTER TABLE "<Table>" ENABLE ROW LEVEL SECURITY;` in their migration (`npm run db:check-rls` and the Vercel build fail otherwise). Status columns are plain strings validated in code. `User.name` uses collation `"C"` (byte order, set in the init migration) so the member directory sorts exactly as it did on SQLite; text search uses case-insensitive `contains` (ILIKE).

## Payments
- Membership applications take **no payment** (see "Membership applications" below). Stripe is used only for paid event tickets.
- No `STRIPE_SECRET_KEY` → **mock checkout** (`/[locale]/events/[slug]/checkout`) simulates the ticket payment and confirms the registration.
- `STRIPE_SECRET_KEY=sk_test_...` → Stripe Checkout (hosted, PCI SAQ-A). Live keys (`sk_live_`) are **refused** in code. Tickets are confirmed on return (session verified server-side) and via webhook `POST /api/stripe/webhook` (set `STRIPE_WEBHOOK_SECRET`; locally: `stripe listen --forward-to localhost:3000/api/stripe/webhook`). `/join/checkout` remains only to finish legacy membership sessions.
- No sales tax by default. `salesTaxByState` (empty) can add per-state rates for US addresses; TODO: confirm with an accountant and use Stripe Tax before charging tax.

## QA round 1 defaults (configurable in `src/config/site.ts`)
- Public directory opt-in is **off** by default (`directoryOptInDefault`).
- Student tier: institution + attestation required at join; membership stays `pending_verification` until staff Approve/Reject in Admin → Members.
- Event tickets are charged in **USD** (`eventCurrency`); paid tickets are `pending_payment` until Stripe test/mock confirms.
- Login throttling (`loginRateLimit`, stored in the DB table `LoginThrottle`, so it survives restarts and works across instances): after 5 failures an account is locked for 1 min, doubling with each further failure up to 15 min, and the count resets on success. A per-IP throttle (20 failures, then +0.5 s per attempt up to 5 s) only slows requests and never locks. It is used only behind a trusted proxy (the IP is read `TRUSTED_PROXY_HOPS` entries from the right of X-Forwarded-For): with `TRUSTED_PROXY=true`, or, when `TRUSTED_PROXY` is not set, automatically on Vercel (`VERCEL=1`, set by the platform; Vercel's edge overwrites X-Forwarded-For with the client IP, so it cannot be spoofed there). Any other explicit value (e.g. `TRUSTED_PROXY=false`) turns it off; elsewhere X-Forwarded-For is ignored. To clear a lockout: Admin → Members → account → "Unlock account", or `npm run unlock -- <email>`.
- Anonymous writes are capped (`anonWriteLimits` in `src/lib/rateLimit.ts`): the contact form takes at most 5 messages per email, 10 per IP and 200 in total per hour; signup and join (signed-out) accept at most 5 account attempts per IP and 100 new accounts in total per hour; `/forgot-password` takes 3 requests per email and 10 per IP per hour. Per-email limits count the address in lower case with any `+tag` removed (`x@d`, `X@d` and `x+1@d` share one limit; the stored and emailed address is never changed). The per-IP caps need a trusted proxy (`TRUSTED_PROXY=true`, or automatically on Vercel, see above); the global caps always apply. The daily cron deletes ended one-hour buckets. Accepted limit: anyone can use up an address's 3 reset requests for an hour (that person then gets up to 3 reset emails and must wait), since counting per account would reveal which accounts exist.
- CSP is set per request in `src/proxy.ts` with a nonce plus `'strict-dynamic'`, so script-src has no `'unsafe-inline'`. style-src keeps `'unsafe-inline'` because inline style attributes (React `style={}` and the prototype markup) can't carry nonces. API routes get `default-src 'none'`.
- Dashboard "Recommended for you" is rule-based and says so on the page. No AI or profiling is used.
- CSV exports escape formula-leading characters.
- Payments fail closed: with `NODE_ENV=production` and no Stripe key, checkout shows "Payment unavailable" unless `ALLOW_MOCK_PAYMENTS=true` is set (set in the local `.env` for this private demo only). A key that isn't `sk_test_` always disables payments.
- Rejected students (`REJECTED_STUDENT_POLICY`, default `notice_manual_refund`): staff enter a reason; the member sees the reason on their dashboard (EN/FR); a paid membership is flagged "Manual refund due" in Admin → Members, and staff click "Mark refunded" after refunding in Stripe. Nothing is refunded automatically. `notice_only` skips the flag. The applicant is also emailed the decision and the reason.
- Event type/format labels are translated through `eventLabels` in the config.

## Membership applications (Nov 2026)
- `/join` captures data only: no prices, tax or payment step. Submitting creates the account (if needed) and a membership in status `pending_verification` for any tier (amount/tax 0, no `paymentRef`, `autoRenew` false), audit `membership.application_submitted`, then redirects to `/my/billing?applied=1` (My membership), which says the ADAIG team point of contact (POC) will be in touch. An acknowledgement email goes to the applicant and a notification to `CONTACT_TO_EMAIL`.
- Staff approve or reject in Admin → Members ("Application review" column). Approve makes the membership active for one year and the user a member; reject shows the reason on the member's dashboard. No refund is flagged because nothing was paid.
- `pending_verification` is never auto-expired. Legacy unpaid `pending` orders can still be canceled from `/join` or the dashboard; `/join/checkout` only completes a legacy Stripe session, then redirects to the dashboard.
- **Renewals and auto-lapse:** there are no automatic renewals or payments yet. Once an active membership's renewal date has passed, the member's dashboard shows "Renewal due — our team will contact you", and the daily cron emails one renewal reminder per renewal period (only while the renewal date passed within the last 14 days, so the first production run sends no backlog). After a 30-day grace period (`LAPSE_GRACE_DAYS` in `src/lib/membership.ts`) the membership becomes `lapsed` (slot freed, member → guest unless another membership is active; admins keep their role; audit `membership.lapsed_auto`, actor `system`). This runs lazily when the member opens their dashboard, billing or directory page (and on `/join` and the admin member pages), and for everyone in the daily cron job / `npm run expire-unpaid-orders`. Staff can extend the renewal date before then, or reactivate a lapsed membership in Admin → Members. When a membership lapses automatically (in the cron, lazily or via the script), the next cron run emails a lapse notice, for lapses of the last 7 days only; a lapse marked by staff sends nothing.

## Admin Portal users & roles (RBAC, round 7)
- **Who is who.** Admin Portal users are `User` rows with `role = "admin"`; they are created and managed **only** in Admin → Users. Association accounts (`guest` / `member`) are managed **only** in Admin → Members. The Members list, its tab counts, the dashboard KPIs and `/api/admin/members.csv` exclude admin accounts, and every Members action treats an admin target as "not found" (so a Member Manager can't reset a Super Admin's password or change their email). Members → New account always creates a guest (a membership tier makes it a member). Users never converts a member into an admin or back: an email already used by **any** account (member, guest, admin) is refused when creating an admin user; staff who are also members use a separate member account. Existing admins keep their membership rows unchanged (shown read-only on their Users page). Admin accounts can't apply for membership on `/join`.
- **Schema** (migration `20261112120000_admin_rbac`, additive only): table `AdminRole` (`id`, unique `name`, `description`, `permissions` JSONB, `isSystem`, timestamps; RLS on, no Data API grants), `User.adminRoleId` (nullable FK → `AdminRole`, **ON DELETE RESTRICT**: a role in use can't be deleted) and `User.active` (default true). The migration creates the system role **Super Admin** (id `sys_super_admin`) and gives it to every existing admin, so production admins keep full access after the deploy. Post-deploy check: `SELECT email FROM "User" WHERE role = 'admin' AND "adminRoleId" IS NULL;` must return no rows (otherwise re-run the migration's final `UPDATE`).
- **Permissions** (`src/lib/permissions.ts`, pure TypeScript shared by the server, the UI and the seed): modules × actions stored as `{ "<module>": ["view", …] }`.

  | Module | Actions | Covers |
  |---|---|---|
  | `members` | view, create, edit, delete | Association accounts, applications, memberships, CPE, member CSV |
  | `events` | view, create, edit, delete | Events, registrations, attendance, registration CSVs |
  | `messages` | view, edit | Contact inbox (edit = mark handled / reopen), messages CSV |
  | `users` | view, create, edit | Admin Portal users (edit = name/email, role, activate/deactivate, password reset, unlock; no delete: deactivate instead) |
  | `roles` | view, create, edit, delete | Roles and their permissions |
  | `system` | view, edit | Overview (dashboard), Settings (edit = save), Audit log + CSV, System status, planned-tool previews |

  Create/Edit/Delete imply View. Stored JSON is normalised and fails closed: unknown modules or actions, malformed JSON, or an admin without a role grant **nothing**. Super Admin always has every permission, whatever its stored JSON says. Seeded example roles (local seed only): Member Manager, Event Manager, Viewer (no Users, Roles or system access).
- **Enforcement** (`src/lib/rbac.ts`): pages call `requireAdminPermission(locale, module, action)` (no permission → `/admin/no-access`; members and guests → `/my/billing`; signed out → login), server actions `assertAdminPermission` / `checkAdminPermission` (refused and audited as `admin.permission_denied`), API routes `apiAdminPermission` (403). The sidebar shows only viewable modules and buttons/forms for missing actions are hidden, but the server checks are what count. Permission edits apply on each user's next page load; a role change, deactivation or password reset also ends the user's sessions.
- **Safety rules** (server-side): Super Admin can't be renamed, changed or deleted; the **last active Super Admin** can't be deactivated, given another role or delete their own account; nobody can deactivate themselves, change their own role, edit their own role, or reset their own password through Users (use Profile & privacy); nobody can grant permissions they don't hold (in a role definition or by assigning a role), or manage a user or role with more permissions than their own; only a Super Admin can assign Super Admin; a role still assigned to someone can't be deleted. Passwords follow the usual policy (12–128 characters, not common, not the email), are typed twice and never shown or logged. Every user and role change is in the audit log (`admin_user.*`, `admin_role.*`).
- **Restoring a Super Admin** (e.g. every Super Admin was deactivated by direct database edits, or the last one is locked out): an operator with database access runs, against the right database,
  ```sql
  UPDATE "User" SET active = true, "adminRoleId" = 'sys_super_admin', "sessionVersion" = "sessionVersion" + 1
  WHERE email = '<admin email>' AND role = 'admin';
  ```
  (the `sessionVersion` bump signs out any old session; drop it to keep them). If the account is also locked, `npm run unlock -- <email>`. If the `sys_super_admin` row itself is missing, re-run the `INSERT … ON CONFLICT DO NOTHING` from the `20261112120000_admin_rbac` migration first. There is no app UI or script for this on purpose.

## Email (SMTP)
All email is sent by the server through one module, `src/lib/email` (nodemailer; nothing else imports it): `sendEmail()` never throws, so a mail problem never breaks a form, an approval or a sign-up. The action is saved first and the email goes out afterwards: the contact, join and approve/reject emails (and the reset link, the Stripe-return ticket confirmation and event cancellation notices) are sent in the background after the response (Next `after()`), so nobody waits on SMTP; the other emails are sent before the page answers. Every email uses one branded layout (600 px, table-based, inline CSS, logo `public/assets/email-logo.png` loaded from the site URL) with a plain-text version, and user-entered text is escaped. SMTP credentials live only in environment variables. They never appear in the browser, the database or the logs.

| Variable | Example / default | Notes |
|---|---|---|
| `SMTP_HOST` | `smtp.zoho.in` | Empty = email **not configured**: nothing is sent and each email is logged as `skipped` (local dev, tests). |
| `SMTP_PORT` | `465` (default) | `587` = STARTTLS. |
| `SMTP_SECURE` | default: `true` on port 465, else `false` | `true` = SSL/TLS from the start. With `false`, STARTTLS is **required** for any host other than localhost. |
| `SMTP_USER` / `SMTP_PASSWORD` | the sending mailbox and its password | Set both or neither (local Mailpit needs none). With Zoho 2FA, use an **app-specific password**. |
| `CONTACT_FROM_EMAIL` | `ADAIG <info@your-domain>` | The From header of every email, either `Name <address>` or a plain address. It must be the SMTP mailbox or one of its aliases. |
| `CONTACT_TO_EMAIL` | `info@your-domain` | The association inbox: contact-form and membership-application notifications go here. |
| `NEXT_PUBLIC_SITE_URL` | `https://your-domain` | Absolute links and the logo in emails (fallback `APP_URL`, then `http://localhost:3000`). Must be **https** and have the **same host as `APP_URL`** (when set): otherwise the Vercel build **fails** (`scripts/check-env.mjs`), because password reset links carry live tokens. In production an `http://` origin is upgraded to `https://` (except localhost). |
| `EMAIL_UNVERIFIED_HOURLY_CAP` | `60` (default) | Send budget for emails to addresses a visitor typed (see "Send budget" below): the most such emails per hour, all recipients together (per pool: acknowledgements / reset links). |

**ADAIG addresses:** the domain is **`adaig.org`** (mailbox `info@adaig.org`, e.g. `CONTACT_FROM_EMAIL="ADAIG <info@adaig.org>"`, `CONTACT_TO_EMAIL=info@adaig.org`). Check the spelling when setting the variables: a typo `adiag.org` was found in `.env` and corrected (with it, Zoho refuses the sender address and inbox notifications would go to a different domain).

**Emails sent** (16 kinds, English only for now; the `kind` is stored in `EmailLog`; every email has Reply-To = `CONTACT_TO_EMAIL` unless noted). Code: `src/lib/notify/{contact,membership,account,events}.ts`. Deleted accounts and deactivated Admin Portal accounts never receive email. Each email has a `dedupeKey`, so double submits, the Stripe return page plus the webhook, and cron re-runs send it once.

| Kind | Trigger | Recipient | Notes |
|---|---|---|---|
| `contact.notify` | `/contact` message saved | `CONTACT_TO_EMAIL` | Reply-To = sender; the full message. Background (`after()`). Skipped when `CONTACT_TO_EMAIL` is not set. |
| `contact.ack` | same | the sender | Does not echo the name, organization or message. Background. |
| `join.ack` | `/join` application submitted | the applicant | Says nothing was charged; mentions the new account when one was created. Background. |
| `join.notify` | same | `CONTACT_TO_EMAIL` | Reply-To = applicant; applicant details and a link to the member page. Background. |
| `membership.approved` | Admin → Members: approve an application | the member | Tier and renewal date. Background. |
| `membership.rejected` | Admin → Members: reject an application | the applicant | The reason (or "No reason was given"); mentions a manual refund when one is flagged. Background. |
| `signup.welcome` | `/signup` creates a free guest account | the new guest | Not sent when the address already has an account. |
| `password.reset_link` | `/forgot-password` | the account holder (active, not deleted) | Single-use link, 60 min; the token is only in the link, never logged. Background. Unknown addresses get the same page answer and no email. |
| `password.changed` | password set with a reset link, or Profile → Change password | the account holder | Security notice. |
| `password.reset_by_staff` | Members: temporary password; Users: set a new password | the account holder | Never contains the password. Users: active users only. |
| `email.changed` | Members or Users: sign-in email changed by staff | the **old** address | The new address is shown masked. Users: active users only. |
| `account.deleted` | Profile → Delete my account, or staff delete in Members | the pre-deletion address | The `EmailLog` row's address is anonymized afterwards. |
| `event.registered` | seat confirmed: free registration, mock ticket, Stripe return or webhook | the registrant | Joining instructions when the event has them. Stripe return and webhook share one dedupe key (one email). |
| `event.cancelled` | Admin → Events: cancel an event | every confirmed registrant | Mentions a refund for paid tickets. Background, one email at a time. A restore then a new cancellation emails again. |
| `membership.renewal_due` | daily cron: renewal date passed within the last 14 days | the member | One per renewal period. No backlog: older renewal dates are not emailed. |
| `membership.lapsed` | daily cron: automatic lapse (`membership.lapsed_auto`, from the cron, lazy housekeeping or `npm run expire-unpaid-orders`) within the last 7 days | the former member | Staff-marked lapses are not emailed. The script itself sends nothing; the next cron run does. |

The cron sends at most 100 emails per kind per run (about 40 s budget); the rest go out on the next run. **Not emailed** (on purpose): Admin → Users create user and Members → New account (no invitation), granting, reactivating, canceling or changing a membership or its renewal date, marking a membership lapsed, role changes, activation/deactivation, unlock, CPE edits, event create/edit/publish/restore/delete, canceling a single registration, attendance, joining details added later, legacy membership payments, honeypot or rate-limited submissions, and sign-up or join with an existing email.

**Send budget (anti-flood):** `contact.ack`, `signup.welcome`, `join.ack` and `password.reset_link` go to an address someone typed on the website, which nobody has verified. To stop the site being used to flood a mailbox (or use up the Zoho sending quota), these kinds have a budget counted from `EmailLog` over the last hour, in two separate pools — the three acknowledgements together, and password reset links on their own (so a flood of acknowledgements can never block a real password reset): per pool, at most **3 per recipient** (lower case, `+tag` removed) and at most `EMAIL_UNVERIFIED_HOURLY_CAP` (default 60) in total. Over budget, the email is not sent and is logged as `skipped` with error `budget`; the message, account, application or reset token is still saved, and the visitor sees the usual answer. Staff notifications (`contact.notify`, `join.notify`) and all other emails are not limited. Skipped rows don't count, so the block ends an hour after the flood stops.

**Zoho Mail:** host `smtp.zoho.in` (India data centre; `smtp.zoho.com` for .com accounts), port `465`, SSL (`SMTP_SECURE` can stay unset). If the mailbox is on an organisation (custom-domain) plan and the login is refused, use `smtppro.zoho.in`. For good deliverability, publish Zoho's SPF and DKIM records (and a DMARC record) for the sending domain (Zoho Mail Admin → Domains → Email configuration).

**Vercel setup:** Project → Settings → Environment Variables, for Production (and for Preview only if previews should send real email): add the variables above and mark `SMTP_PASSWORD` as **Sensitive**, then redeploy (variables apply only to new deployments). The build (`scripts/check-env.mjs`) **warns** but does not fail when SMTP variables are missing. It **fails** when `NEXT_PUBLIC_SITE_URL` is not an `https://` URL or its host differs from `APP_URL`'s host (only the host is compared, so `APP_URL` may still be `http://`). Vercel allows outgoing SMTP on ports 465 and 587.

**Check real delivery:** run `npm run email:test -- you@example.com` on a machine whose environment (or `./.env`) holds the production SMTP variables. It prints the settings without the password, connects and logs in, sends one branded test email and prints the SMTP server's answer (e.g. `250 Message received`) or the exact error. Exit code 0 = accepted by the server; then check the inbox and the spam folder. It writes no database row.

**EmailLog table:** one row per email: `kind` (e.g. `contact.notify`, `password.reset_link`), `toEmail`, `subject`, `status` (`sent` | `failed` | `skipped`), `error` (short reason, never secrets; any email address in an SMTP reply is replaced with `[address]`, and account deletion scrubs the person's rows the same way), `messageId`, `dedupeKey`, `userId`, `createdAt`. Bodies are never stored. A row is written as `failed` / "sending (interrupted if this persists)" before the SMTP call and updated afterwards, so an interrupted send stays visible. `dedupeKey` (unique) stops double sends (double submits, cron re-runs): a key that was already sent is answered `duplicate`, and a key whose earlier attempt failed or was skipped is retried. Look up recent failures with:
`SELECT "createdAt", kind, "toEmail", status, error FROM "EmailLog" WHERE status <> 'sent' ORDER BY "createdAt" DESC LIMIT 50;`

**Local development and tests (Mailpit):** run [Mailpit](https://mailpit.axllent.org/) (`brew install mailpit && mailpit`, or `docker run -p 8025:8025 -p 1025:1025 axllent/mailpit`) and start the app with `SMTP_HOST=127.0.0.1 SMTP_PORT=1025 SMTP_SECURE=false` (no user or password) and `CONTACT_FROM_EMAIL="ADAIG Website <info@adaig.test>" CONTACT_TO_EMAIL=info@adaig.test`. Every email lands in the Mailpit inbox at http://127.0.0.1:8025, and nothing leaves the machine. The e2e helpers in `tests/e2e/support/mail.ts` (`waitForEmail`, `listEmails`, `clearMailbox`) read it through its API (`MAILPIT_URL`, default `http://127.0.0.1:8025`).

**Troubleshooting** (the `error` column and `npm run email:test` show the reason):
- `skipped` with error `SMTP not configured`: `SMTP_HOST` is not set in that environment. Set it and redeploy.
- `skipped` with error `budget`: the send budget for visitor-typed addresses was reached (see "Send budget"). Many such rows in a short time mean someone is abusing a public form.
- `EAUTH 535 …` (authentication failed): wrong `SMTP_USER` / `SMTP_PASSWORD`; with 2FA, generate an app-specific password in Zoho; for organisation accounts, try `smtppro.zoho.in`.
- `553 … not allowed to relay` / sender rejected: `CONTACT_FROM_EMAIL` is not the login mailbox or one of its aliases.
- `ETIMEDOUT` / `ESOCKET` / `ECONNREFUSED`: wrong host or port, or `SMTP_SECURE` does not match the port (465 = SSL, 587 = STARTTLS). Timeouts are 10 s with one retry, so a failing send takes up to about 20 s.
- `wrong version number` (TLS): `SMTP_SECURE=true` on a STARTTLS port, or the other way round.
- `invalid recipient address`: the stored address is not a valid email address, so nothing was sent.
- Sent but not received: check spam, SPF/DKIM/DMARC for the sending domain, and Zoho's sent folder / outgoing logs.

## Deploying to Vercel (with Supabase)
Production uses a hosted **Supabase Postgres** database (Vercel's file system is read-only, and SQLite is no longer supported). The app connects through Supabase's **transaction pooler** (Supavisor, port 6543 — right for serverless functions); migrations run over the **direct/session** connection.

1. **Database:** Vercel → Project → Storage → Create/Connect Database → **Supabase**, for Production and Preview. The integration adds `POSTGRES_PRISMA_URL` (pooled) and `POSTGRES_URL_NON_POOLING` (direct), which the app and build use automatically. Without the integration, set `DATABASE_URL` (pooled, `…:6543/postgres?pgbouncer=true&sslmode=require`) and `DIRECT_URL` (`…:5432/postgres?sslmode=require`) from Supabase → Connect; these win over the integration names.
2. **Environment variables** (Project → Settings → Environment Variables, Production and Preview):
   - `AUTH_SECRET` — required (`openssl rand -base64 32`); production rejects short or placeholder values.
   - `CRON_SECRET` — required for the daily scheduled job in `vercel.json` (expires stale unpaid orders, lapses memberships 30 days past their renewal date, emails renewal reminders and lapse notices, prunes old throttle rows and used/expired password reset tokens); Vercel sends it as a Bearer token. Without it the job answers 503 (memberships then lapse only when the member or staff open the relevant pages, and no renewal reminders or lapse notices are emailed).
   - `TRUSTED_PROXY`, `TRUSTED_PROXY_HOPS` — optional on Vercel: when `TRUSTED_PROXY` is not set, the app trusts Vercel's `X-Forwarded-For` automatically (`VERCEL=1`), so sign-in throttling and the contact/sign-up/password-reset limits also count per client IP (hops default 1). Set `TRUSTED_PROXY=false` to turn per-IP limits off; elsewhere (not Vercel) set `TRUSTED_PROXY=true` only behind a proxy that sets X-Forwarded-For.
   - The database variables from step 1.
   - Email: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD` (Sensitive), `CONTACT_FROM_EMAIL`, `CONTACT_TO_EMAIL`, `NEXT_PUBLIC_SITE_URL`: see "Email (SMTP)". Without them the site works but sends no email (the build warns). `NEXT_PUBLIC_SITE_URL` must be `https://` with the same host as `APP_URL`, or the build fails.
   - Optional: `APP_URL` (the site URL), `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` (test keys only), `DB_POOL_MAX` (default 5 per instance).
3. **Deploy:** `npm run vercel-build` (used automatically by Vercel) runs `scripts/check-env.mjs` (a missing or wrong variable fails the build with a clear message), `prisma generate`, `prisma migrate deploy` (applies pending migrations, including the RLS lockdown), `scripts/check-rls.mjs` (fails if any public table lacks RLS), then `next build`. Node version: `engines` in package.json (Vercel uses Node 26). Functions run in **Mumbai (`bom1`, `vercel.json` → `regions`)** next to the Supabase database (ap-south-1); change both together if the database moves.
4. **Seed once (optional):** from your machine, against the hosted database (direct URL):
   `ALLOW_REMOTE_DB=1 DIRECT_URL="<direct postgres url>" SEED_PASSWORD="<strong password>" npm run db:seed`.
   The seed refuses any non-localhost database unless `ALLOW_REMOTE_DB=1` and `SEED_PASSWORD` are set, and refuses if users already exist (it wipes all tables) unless `SEED_FORCE=1`. Change or remove the demo accounts before a public launch. The seeded events (two webinars with fixed dates, a proposed meetup and summit) are sample data: confirm, edit or unpublish them in Admin → Events.
5. **Monitoring:** point an uptime monitor at `/api/health`.

**Upgrading a database created before migrations** (the earlier `prisma db push` deployment): don't let the first deploy run against it unprepared — `migrate deploy` stops with "database schema is not empty" (P3005). Back it up, then with `DIRECT_URL` pointing at it run `npx prisma db execute --file prisma/upgrade-from-db-push.sql` (timestamps → timestamptz as UTC, collation, new indexes; data kept), `npx prisma migrate resolve --applied 20261110134554_init`, `npx prisma migrate deploy` and `npm run db:check-rls`. If the hosted data is disposable demo data, an empty database plus `npm run db:seed` (with `SEED_PASSWORD`) is simpler.

Page content in `src/content` is read at runtime, so `next.config.ts` includes it in the serverless bundle (`outputFileTracingIncludes`).

## Testing (end-to-end, Playwright)
`tests/e2e` holds a Playwright suite that drives the running app in a browser and checks the database: public pages EN/FR (status, console errors, no horizontal overflow at 390px), security headers/CSP nonce, auth and lockout, join → approval, member area, contact → inbox, admin members/events/messages/settings/audit/system, Admin Portal users and roles (RBAC: sidebar and direct URLs per role, hidden buttons, Server Action and CSV replays by under-privileged admins, escalation and last-Super-Admin rules), CSV access control, Server Action authorization replays, cron auth and Supabase RLS. The database must be migrated (the global setup stops with a clear message if `AdminRole` / `User.active` are missing).
```bash
npm run build && npm start                 # the suite tests a running app (default http://localhost:3000; E2E_BASE_URL to change)
export E2E_DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres   # REQUIRED: the same local database the app uses
npx playwright install chromium            # once (or use a local Chrome: PW_CHROME_PATH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome", or PW_CHANNEL=chrome)
npm run test:e2e                           # desktop project (all tests) + mobile project (tests tagged @smoke)
npm run test:e2e -- --project=desktop specs/admin-events.spec.ts   # one file
npm run test:e2e:smoke                     # @smoke tests only
npm run test:e2e:report                    # open the HTML report (traces/screenshots of failures)
npm run test:e2e:cleanup                   # remove e2e data after an interrupted run
```
- **Data**: tests create their own throwaway data (users `e2e-<run>-<n>@example.test`: no `+tag`, because per-address limits and the email send budget ignore `+tags`; ids `e2e-…`, events `E2E …`, admin roles `E2E Role …`) and only read the seed accounts (`Password123!`, override with `E2E_SEED_PASSWORD`). Tests that change settings undo it through Admin → Settings in `finally`, so the app's settings cache stays correct. Helpers in `tests/e2e/support/db.ts`: `createUser({ role, adminRoleId | adminRole, active })` (an admin defaults to Super Admin), `createAdminRole({ permissions })`, `createAdmin(permissions)`, `ROLE_PRESETS` (the seed roles' permission sets), `setActive`, `setAdminRole`, `setRolePermissions`, `deactivateOtherSuperAdmins` (returns its undo); fixtures `loginAs(user)` (any portal home, including admins with a narrow role or none) and `loginAsAdmin(permissions)`.
- **Rules for specs**: users created through the UI use `uniqueEmail()`, roles created through the UI use `uniqueName("Role")`; never change a seed account's role, status or password through the UI (the shared signed-in sessions would end for the rest of the run); temporary database changes to seed rows go in `try/finally`. `ContentPage` rows a test needs are inserted with `e2eId()` ids and deleted directly in the database by the cleanup (there is no content admin UI any more).
- **Cleanup**: the global setup first cleans up after an unfinished earlier run, then **purges every e2e-marked row left by earlier runs** (users `e2e-…@example.test` or older `e2e+…@example.test` / `e2e-…` ids / `E2E …` names on `@example.test`, `E2E …` roles, e2e events, messages, throttle rows, `e2e-…` content rows and their audit rows; nothing without a marker is touched; this purge refuses any non-local database, with no override), makes sure the seed accounts are active and the seed admins are Super Admins, then snapshots the database (tagged with its host/port/name: a snapshot is never applied to another database). The global teardown deletes everything the run wrote (markers + a per-test ledger of unmarked rows such as admin audit entries and roles created through the UI; users holding an e2e role are removed before the role, as the foreign key requires), restores seed users (including role, `adminRoleId` and `active`), seed events and seed roles, compares with the snapshot and prints before/after table counts (`tests/.state/db-report.json`). Rows written meanwhile by other people using the same database are left alone and reported. `E2E_RESTORE=strict` (CI / dedicated database) restores every table exactly and fails on any difference; `E2E_KEEP_DATA=1` skips cleanup for debugging.
- **Settings**: one worker (tests share the seed accounts and the app cache), retries only on CI (`CI=1`), traces kept on failure.
- **Email send budget**: a full run sends about 50 emails to visitor-typed addresses within the hour, close to the production default of `EMAIL_UNVERIFIED_HOURLY_CAP` (60), so start the app under test with `EMAIL_UNVERIFIED_HOURLY_CAP=1000`. The budget test (`email-security.spec.ts`) briefly inserts `E2E_EMAIL_UNVERIFIED_HOURLY_CAP` (default 1000) synthetic log rows, so it works with any server cap up to that.
- **Safety**: the suite writes and deletes rows, so it reads its database only from `E2E_DATABASE_URL` (never from `.env`) and refuses to start unless that host and the `E2E_BASE_URL` host are local (`localhost`, `127.0.0.1`, `::1`); overrides `ALLOW_REMOTE_DB=1` / `E2E_ALLOW_REMOTE=1` exist for a dedicated test database only. Never run it against production.
- **CI**: start Supabase (`npx supabase start`), `npm ci && npm run setup && npm run build`, `npx playwright install --with-deps chromium`, then `CI=1 E2E_RESTORE=strict E2E_START_SERVER=1 E2E_DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres npm run test:e2e` (Playwright starts `npm start` itself); publish `playwright-report/` and `test-results/e2e-junit.xml`.
